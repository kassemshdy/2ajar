# Deployment (Railway → 2ajar.halyoon.com)

Railway project **`2ajar`** in the **PulseX** workspace. One public hostname, `2ajar.halyoon.com`, points at the
`web` service. The browser only talks to `web`. Next.js proxies `/api/v1/*` and `/media/*` to `api` over Railway's
private network, so auth cookies are first-party and the API has no public domain.

```
Browser ─▶ Cloudflare DNS ─▶ Railway edge ─▶ web (Next.js) ──private──▶ api (FastAPI) ─▶ Postgres
                                                                         └────────────▶ bucket ajar-media (S3)
```

## Services

| Service | Source | Build | Health check |
|---|---|---|---|
| `web` | `kassemshdy/2ajar` (`main`) | `infra/docker/web.Dockerfile`, config `apps/web/railway.json` | `/api/health` |
| `api` | `kassemshdy/2ajar` (`main`) | `infra/docker/api.Dockerfile`, config `apps/api/railway.json` | `/readyz` |
| `Postgres` | Railway PostgreSQL | managed | managed |
| `ajar-media` | Railway bucket (S3-compatible, private) | – | – |

The worker (`apps/worker`, freshness report) is not deployed yet. It only logs counts today; M4 adds reminders.

## Deploy flow

- Push to `main` → Railway builds both services.
- `api` pre-deploy: `alembic upgrade head && python -m app.seed ${SEED_DEMO:+--demo}`. It seeds locations always and demo
  data only when `SEED_DEMO` is set. Both are idempotent. A failed migration fails the deploy and the old version keeps serving.
- Migrations are expand-only per release, so the previous release still works against the new schema.

## Rollback

Redeploy the previous successful deployment of the affected service in Railway (Deployments → ⋯ → Redeploy).
Never run `alembic downgrade` in production without a fresh backup and a reviewed downgrade.

## Custom domain (Cloudflare)

`halyoon.com` DNS is on Cloudflare. After `2ajar.halyoon.com` is added to `web` in Railway, add the records Railway
shows:

1. `CNAME 2ajar → <value from Railway>`, **DNS only (grey cloud)** until Railway shows the certificate as issued.
2. The `TXT _railway-verify.2ajar` record, if Railway asks for one.
3. Optional later: orange cloud with SSL/TLS mode **Full (strict)**, then set `FORWARDED_TRUSTED_HOPS=3`.

## Telegram monitoring

The API posts to a Telegram chat when an account is created, a listing is created or published, a lead arrives
(phone masked, message omitted), or a CSV import creates drafts. Sending is best-effort and never blocks requests.

1. In Telegram, message **@BotFather** → `/newbot` → copy the token.
2. Add the bot to your group (or start a DM with it) and send it any message.
3. Open `https://api.telegram.org/bot<TOKEN>/getUpdates` in a browser and copy `chat.id` (groups are negative numbers).
4. In Railway → `api` → Variables, set `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`. Railway redeploys automatically.
5. Register a test account on the site. A "🆕 New … account [staging]" message should arrive.

## Go-live switch (demo → real inventory only)

1. Set `DEMO_MODE=false` on `api`. Demo listings disappear from the site immediately.
2. Remove `SEED_DEMO`.
3. Optionally delete demo data permanently: run `python -m app.seed --purge-demo` once (e.g. as a temporary
   pre-deploy command, then revert).
4. Set `ENV=production`. The API refuses to start if `DEMO_MODE=true` in production.

## Backups

Enable Railway Postgres backups (daily, ≥7-day retention) in the Postgres service settings, and take a manual
backup before any migration that rewrites data. Restore drills: quarterly, into a scratch database.

## Database diagnostics

Any diagnostics connection (e.g. a PostgreSQL MCP) must use a read-only role:
```sql
CREATE ROLE diag_ro LOGIN PASSWORD '<secret>';
GRANT CONNECT ON DATABASE railway TO diag_ro;
GRANT USAGE ON SCHEMA public TO diag_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO diag_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO diag_ro;
ALTER ROLE diag_ro SET default_transaction_read_only = on;
```
